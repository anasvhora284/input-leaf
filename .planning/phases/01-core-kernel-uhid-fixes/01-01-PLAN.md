# Plan 01-01: Core Kernel UHID Stability & Stream-Model Purge

<objective>
Stabilize the Linux kernel `/dev/uhid` character device integration in `com.inputleaf.android.shizuku.uhid`:
1. Make `UhidChannel.stopReader()` cleanly stoppable using bounded POSIX polling / timeout checks so `reader.join()` never times out and prevents zombie thread accumulation (UHID-01, #48).
2. Update `UhidChannel.awaitReady()` to exit upon `sawStart || sawOpen` so devices on OEM ROMs (ColorOS, EMUI, etc.) that do not emit userspace `UHID_OPEN` don't stall for the full timeout window (UHID-02, #49).
3. Purge dead stream-model methods (`waitForStart()`, `drainPayload()`) and unreachable deferred INPUT2 queue (`deferredReports`, `allowInputLocked()`) from `UhidProtocol` and `UhidChannel` (UHID-03, #50).
</objective>

<context>
Linux `/dev/uhid` (`drivers/hid/uhid.c`) is a packet message queue where each `read()` syscall consumes and frees an entire `struct uhid_event` (4376 bytes). Standard Java `FileInputStream.read()` blocks in an uninterruptible kernel wait queue. Furthermore, `UHID_START` is guaranteed by hid-core probe, while `UHID_OPEN` is an optional userspace notification that some OEM ROMs omit. Lastly, `createDevice()` blocks until completion so callers never write reports before initialization, making the deferred reports queue dead code.
</context>

  <action>
    Refactor `UhidChannel.startReader()` and `stopReader()` in `app/src/main/java/com/inputleaf/android/shizuku/uhid/UhidChannel.kt`:
    1. In `startReader()`, avoid blocking indefinitely in `input.read()`.
       - When `readPfd` is non-null (Android runtime with real `/dev/uhid` file descriptor):
         Use `android.system.Os.poll` with `android.system.StructPollfd` set for `OsConstants.POLLIN` with a bounded timeout (50ms). If `poll` returns 0 (timeout), loop back and re-evaluate `!closed.get() && !readerStop.get() && !Thread.currentThread().isInterrupted`. If `poll` indicates readable data, proceed to read the full `UhidProtocol.EVENT_PACKET_SIZE` packet. Catch `ErrnoException` (e.g. `EBADF`, `EINTR`) and break the loop cleanly.
       - When `readPfd` is null (JVM tests and in-memory streams using `PipedInputStream`):
         Check `input.available()`. If `input.available() <= 0`, perform a brief cooperative pause (e.g. `Thread.sleep(10)` or `readinessConfig.sleeper(10)`) checking `readerStop.get()`, or read with standard EOF handling.
    2. In `stopReader()`:
       Set `readerStop.set(true)`, close `readPfd` safely with `runCatching`, interrupt `readerThread`, and call `reader.join(READER_JOIN_MS)`.
    3. Add a test in `UhidChannelReadinessTest.kt` verifying that creating and closing a channel terminates the reader thread promptly without leaking alive threads or exceeding `READER_JOIN_MS`.
  </action>

<task id="01-01-02" name="Update awaitReady to exit on sawStart or sawOpen" type="refactor">
  <read_first>

    app/src/test/java/com/inputleaf/android/shizuku/uhid/UhidChannelReadinessTest.kt
  </read_first>
  <action>
    Modify `UhidChannel.awaitReady()` and readiness assertions:
    1. In `UhidChannel.kt`, update the readiness wait loop:
       ```kotlin
       val openDeadline = readinessConfig.nanoTime() +
           TimeUnit.MILLISECONDS.toNanos(readinessConfig.openTimeoutMs)
       while (readinessConfig.nanoTime() < openDeadline &&
              !wait.sawStart.get() &&
              !wait.sawOpen.get()) {
           readinessConfig.sleeper(readinessConfig.pollIntervalMs)
       }
       if (!wait.sawStart.get() && !wait.sawOpen.get()) return
       ```
    2. Ensure that if either `sawStart` or `sawOpen` is set, the loop terminates immediately without waiting for `openTimeoutMs` to expire.
    3. In `UhidChannelReadinessTest.kt`:
       - Update the test formerly named `a kernel START alone is not treated as readiness` to `START completes readiness without burning the whole timeout`.
       - Assert that when `UHID_START` is received, `clock.elapsedMs()` is strictly less than `openTimeoutMs` (300ms) and the presence probe can proceed if configured.
       - Verify that when neither `START` nor `OPEN` is sent, `awaitReady()` degrades gracefully after bounded timeout without hanging.
  </action>
